## Podsumowanie w jednym akapicie

System działa i jest wdrożony, ale ma **pięć usterek klasy P0**, z których dwie kosztują realne pieniądze przy każdej transakcji, a jedna pozwala nowemu klientowi nadpisać stronę istniejącego klienta. Fundament bezpieczeństwa jest przemyślany (scrypt, HMAC, timing-safe compare, weryfikacja podpisów Stripe i Meta, nagłówki bezpieczeństwa, rate limiting) — to nie jest kod amatorski. Problemy leżą gdzie indziej: w **warstwie operacyjnej** (provisioning, idempotencja, współbieżność) i w **braku jakiejkolwiek siatki bezpieczeństwa** — zero testów, zero CI, przy kluczu `sk_live_` w produkcji.

### 2. Hasła właścicieli generowane przez `Math.random()`

**Plik:** `src/lib/provision-site.ts:9-14`

```typescript
function generateTempPassword(): string {
  const chars = 'ABCDEFGHJKMNPQRSTUVWXYZabcdefghjkmnpqrstuvwxyz23456789!@#'
  return Array.from({ length: TEMP_PASSWORD_LENGTH }, () =>
    chars[Math.floor(Math.random() * chars.length)]   // ← nie kryptograficzne
  ).join('')
}
```

To hasło trafia jednocześnie do **konta Supabase Auth** i do **panelu właściciela** (`hashPassword(tempPassword)`, linia 41). `Math.random()` w V8 to xorshift128+ — stan generatora da się odtworzyć z kilku kolejnych wyników. Klient, który zna własne hasło i moment provisioningu, jest w uprzywilejowanej pozycji do przewidzenia haseł sąsiadów w kolejce.

**Fix:** `crypto.randomInt(chars.length)` albo `crypto.randomBytes` + odrzucanie modulo bias.

### 3. Kolizja slugów kasuje stronę istniejącego klienta

**Pliki:** `src/lib/provision-site.ts:102`, `src/lib/generate-site.ts:6-17`

`slug` powstaje wyłącznie z nazwy apartamentu, bez sufiksu unikalności:

```typescript
const slug = toSlug(typedOrder.apartment_name)     // provision-sites/route.ts:45
// ...
.upsert({ ...wszystkie pola... }, { onConflict: 'slug' })   // provision-site.ts:102
```

`sites.slug` ma `unique` w schemacie. Drugi klient, który nazwie apartament „Casa Sol", **nadpisze wiersz pierwszego** — `config`, `owner_email`, `owner_user_id`, `admin_password_hash`, `stripe_account_id`, `expires_at`. Pierwszy klient traci dostęp do panelu i swoją stronę; jego rezerwacje (`bookings.site_id`) zostają przy przejętym wierszu.

Dodatkowo `toSlug` zwraca **pusty string** dla nazw bez znaków łacińskich (cyrylica, chiński, same emoji) — wszystkie takie zamówienia kolidują w jeden wiersz `slug = ''`.

**Fix:** sprawdź zajętość slugu przed insertem i dodaj sufiks (`casa-sol-2`); zamień `upsert` na `insert` (kolizja ma być błędem, nie cichym nadpisaniem); fallback dla pustego slugu.

### 4. Nobooking płaci prowizje Stripe za wszystkich klientów

**Plik:** `src/lib/stripe-connect.ts:141-143`

```typescript
payment_intent_data: {
  transfer_data: { destination: params.accountId },
},
```

To **destination charge** bez `application_fee_amount` i bez `on_behalf_of`. Konsekwencje:

- Merchant of record to **platforma** (Nobooking), nie właściciel apartamentu.
- Prowizję Stripe (~1,5% + 0,25 € w EOG, więcej dla kart spoza) pobiera się z **salda platformy**.
- Do właściciela transferowana jest **pełna kwota** rezerwacji.
- Chargebacki i zwroty obciążają **platformę**.

Przy rezerwacji 1 200 € Nobooking dopłaca ~18 € z własnej kieszeni i nie inkasuje nic. Model przychodowy to jednorazowa opłata za stronę (799–1199 zł / 2 lata) — im lepiej klientom idzie wynajem, tym więcej tracisz.

Dokumentacja utrwala błędny model (patrz Część 2, pkt 1).

**Do decyzji biznesowej, nie tylko technicznej:**
- **(a)** dodać `application_fee_amount` pokrywający prowizję (np. 2%) — najprostsze, ale zmienia ofertę;
- **(b)** przejść na *direct charges* (`stripe.checkout.sessions.create(..., { stripeAccount: accountId })`) — właściciel staje się merchant of record, sam płaci prowizje i odpowiada za chargebacki. To zgadza się z tym, co obiecuje dokumentacja;
- **(c)** świadomie zostawić jako koszt akwizycji — ale wtedy policz go i zapisz w dokumentacji.

Rekomendacja: **(b)**, bo eliminuje też odpowiedzialność za chargebacki cudzych gości.

### 5. Odnowienie subskrypcji bez idempotencji

**Plik:** `src/app/api/stripe/webhook/route.ts:98-132`

Gałąź `orderId` ma zabezpieczenie przed duplikatem (linie 46-55). Gałąź `bookingId` ma (linie 147-150). Gałąź **renewal — nie ma żadnego**:

```typescript
if (renewalType === 'renewal' && renewalSiteId) {
  // ...
  const newExpiry = new Date(currentExpiry.getTime() + 2 * 365.25 * 24 * 60 * 60 * 1000)
  await supabase.from('sites').update({ expires_at: newExpiry, active: true })
```

Stripe **gwarantuje at-least-once delivery** — powtórki są normalnym zjawiskiem, nie awarią. Każde ponowne dostarczenie tego samego zdarzenia dokłada kolejne 2 lata. Trzy powtórki = 6 lat gratis.

**Fix:** zapisuj `stripe_session_id` odnowienia (nowa kolumna albo tabela `renewal_payments`) i sprawdzaj przed przedłużeniem.

## P1 — poważne

### 6. Rezerwacja potwierdzana bez sprawdzenia, czy zapłacono

`src/app/api/stripe/webhook/route.ts:33` reaguje na `checkout.session.completed` i od razu ustawia `status: 'confirmed'`, `stripe_paid: true`. Nie sprawdza `session.payment_status`. Dla metod z opóźnionym potwierdzeniem to zdarzenie potrafi przyjść z `payment_status: 'unpaid'`. Nie sprawdza też, czy `session.amount_total` zgadza się z `booking.total_price`.

**Fix:** `if (session.payment_status !== 'paid') return` + porównanie kwoty.

### 7. Podwójna rezerwacja tych samych dat (TOCTOU)

`src/app/api/sites/[slug]/book/route.ts:80-100` — sprawdzenie kolizji i `insert` to dwie osobne operacje. Dwa równoległe żądania na te same daty oba przechodzą walidację i oba wstawiają rezerwację. W `docs/supabase/booking_schema.sql` **nie ma constraintu wykluczającego** na zakresy dat — tylko `unique (site_id, date)` na `blocked_dates`. Nic tego nie łapie.

**Fix:** constraint w bazie:
```sql
alter table bookings add constraint no_overlap
exclude using gist (
  site_id with =,
  daterange(check_in, check_out, '[)') with &&
) where (status in ('pending','confirmed'));
```
Wymaga `create extension if not exists btree_gist;`. To jedyne rozwiązanie odporne na wyścig.

### 8. Mail onboardingowy cicho się nie wysyła

`src/app/api/stripe/webhook/route.ts:76-77`:

```typescript
const alreadySent = ['onboarding_sent', 'building', 'completed'].includes(order.status)
if (order && !alreadySent) {
```

`order.status` czytane **przed** sprawdzeniem `order &&`. Gdy `order` jest `null` → `TypeError` → łapie go `catch` na linii 85 → mail nigdy nie wychodzi, a log mówi tylko „onboarding email error". Klient zapłacił i nie dostaje nic.

### 9. Cron provisioningu nie ma blokady na równoległe uruchomienia

`vercel.json:5` — harmonogram `* * * * *` (co minutę). `maxDuration = 300`. Jedno przetworzenie zawiera wywołanie LLM, więc łatwo przekracza 60 s. Kolejny run zaczyna się, gdy poprzedni jeszcze pracuje, i widzi te same zamówienia (`site_slug` wciąż `null`) → podwójne konto Auth, podwójne konto Stripe Connect, podwójne maile.

**Fix:** kolumna `provisioning_started_at` + atomowe „zaklepanie" wiersza przed przetwarzaniem, albo advisory lock.

### 10. Provisioning przestanie działać przy 50. kliencie

`src/lib/provision-site.ts:55` — `supabase.auth.admin.listUsers()` domyślnie zwraca pierwszą stronę (50 użytkowników). Ścieżka „użytkownik już istnieje" przy większej liczbie kont nie znajdzie użytkownika → `throw` → zamówienie utknie na stałe.

**Fix:** `listUsers({ page, perPage })` w pętli albo zapytanie po emailu.

### 11. Zmiana hasła nie unieważnia istniejących sesji

`src/app/api/sites/[slug]/owner/password/route.ts` zmienia hash, ale tokeny HMAC pozostają ważne 7 dni (`ownerAuth.ts:7`). Właściciel zmieniający hasło po włamaniu **nie wyrzuca włamywacza**.

**Fix:** kolumna `token_version` w `sites`, w payloadzie tokena, inkrementowana przy zmianie hasła; `verifyOwnerSession` porównuje.

### 12. Prompt injection w bocie Facebook

`src/app/api/facebook/webhook/route.ts:82` wstawia treść publicznego komentarza wprost w wiadomość do modelu:

```typescript
`Krótko odpowiedz na komentarz... Komentarz: "${commentText}"`
```

Ktokolwiek może skomentować post na Twojej firmowej stronie i sterować odpowiedzią bota — bot odpowie publicznie. Może też wymusić `save_lead` z dowolnymi danymi (linie 64-71).

**Fix:** komentarz jako osobny blok oznaczony jako dane niezaufane, instrukcja w `system`, walidacja `save_lead` (format telefonu, długość), oraz — najważniejsze — **komentarze bota tylko po zatwierdzeniu** albo z twardym whitelistem tematów.

## P2 — do zaplanowania

**16. Brak walidacji cen.** `owner/settings/route.ts:80-90` — `Number(patch.pricePerNight)` przyjmuje wartości ujemne, `NaN` i `Infinity`. `NaN` serializuje się do `null` w JSONB, po czym kalkulacja ceny w `book/route.ts:132` daje `NaN` → `amountCents: NaN` → Stripe odrzuca. Waluta ma whitelistę, kwoty — nie.

**17. RODO: „anonimizacja" jest odwracalna.** `admin/guests/[email]/route.ts:46` — `sha256(email)` obcięty do 12 znaków hex. Emaile mają niską entropię; mając listę kandydatów odtwarzasz oryginał w sekundy. Komentarz w kodzie mówi „non-reversible" — to nieprawda. W nomenklaturze RODO to pseudonimizacja, nie anonimizacja, więc dane **nadal podlegają rozporządzeniu**. Fix: losowy UUID zamiast hasha.

**18. Webhook FB przetwarza synchronicznie.** `facebook/webhook/route.ts:117-141` — pętla z `await handleMessage()` przed zwróceniem 200. Meta oczekuje odpowiedzi w ~20 s i ponawia po timeoucie. Wywołanie Claude + DB + wysyłka potrafi to przekroczyć → Meta ponawia → gość dostaje duplikaty. Brak deduplikacji po `message.mid`.

**19. `isBotEnabled` zawodzi „na otwarto".** `claude-bot.ts:40` — `data?.enabled ?? true`. Awaria bazy = bot działa i wydaje pieniądze. Dla wyłącznika awaryjnego domyślna wartość powinna być `false`.

**20. Brak Content-Security-Policy.** `next.config.ts:11-18` ma sześć nagłówków, brakuje CSP — najważniejszego przeciw XSS. Plus: `X-XSS-Protection` jest przestarzały i ignorowany przez współczesne przeglądarki.

**21. Rate limiting w pamięci procesu.** `proxy.ts:11` — `Map` per instancja edge. Rozproszone żądania omijają limit. Kod sam to odnotowuje; przy obecnej skali akceptowalne, ale to nie jest ochrona przed zdeterminowanym atakiem.

**22. Bot używa starszego i droższego modelu.** `claude-bot.ts:82` — `claude-sonnet-4-6`: 3 $/1M wejście, 15 $/1M wyjście. `claude-sonnet-5`: **2 $ / 10 $** — nowszy i o ~33% tańszy. Dodatkowo baza wiedzy leci w `system` przy **każdej** wiadomości bez prompt cachingu; `cache_control: { type: 'ephemeral' }` obniża koszt cache'owanej części o ~90%.

> Uwaga migracyjna: `claude-bot.ts:88` czyta `response.content[0]`. Po włączeniu adaptive thinking pierwszym blokiem bywa `thinking`, nie `text` — trzeba szukać bloku po `type`, nie po indeksie. Format JSON wymuszany promptem warto zamienić na `output_config.format` (structured outputs), co usuwa fallback z linii 93.

**23. Brak walidacji formatu emaila** w `owner/settings/route.ts:54` (`/api/orders` ma ją poprawnie — `orders/route.ts:6`).

# CZĘŚĆ 3 — Czy obecna specyfikacja spełnia swoje zadanie?

Krótka odpowiedź: **spełniła zadanie, do którego powstała, i nie spełnia tego, którego potrzebujesz teraz.**

`docs/superpowers/` zawiera 6 planów i 3 specyfikacje z maja 2026. To specyfikacje **budowlane** — „jak zbudować funkcję X". Świetnie się sprawdziły: system powstał i działa. Ale mają trzy cechy, które teraz przeszkadzają:

**1. Są zamrożone w czasie.** Ostatni spec to 7 maja. System rezerwacji, panel właściciela i odnowienia mają plany, ale nie mają specyfikacji. Nie ma dokumentu opisującego, jak system wygląda **dziś**.

**2. Opisują funkcje, nie niezmienniki.** Nigdzie nie jest zapisane: „slug jest unikalny w skali platformy", „rezerwacja nie może nakładać się na inną", „webhook musi być idempotentny", „prowizję Stripe płaci właściciel". Gdyby te zdania istniały, cztery z pięciu usterek P0 byłyby złapane przy pisaniu kodu — bo naruszają zapisane reguły. **Wszystkie usterki P0 to naruszenia niezmienników, których nikt nigdy nie zapisał.**

**3. Nie ma modelu wielodostępności.** To najgłębszy problem. Projekt zaczął się jako strona jednego apartamentu (Casa Sol), a stał się platformą SaaS obsługującą wielu klientów. Specyfikacje nadal myślą kategoriami „strona apartamentu". Stąd bierze się kolizja slugów: w modelu jednego apartamentu slug z nazwy jest oczywisty i poprawny. W modelu platformy — to bomba.

## Czego brakuje

Nie kolejnego planu funkcji. Brakuje **specyfikacji operacyjnej** — jednego dokumentu, który definiuje:

- **Model najemcy:** czym jest tenant, co go izoluje, co jest globalne (slugi, konta Auth, konta Stripe)
- **Niezmienniki:** lista zdań, które muszą być prawdziwe zawsze — testowalna, jedno zdanie = jeden test
- **Tryby awarii:** co się dzieje, gdy Stripe nie odpowiada, gdy Anthropic zwraca błąd, gdy cron przekracza limit czasu, gdy webhook przychodzi dwa razy
- **Model pieniędzy:** kto płaci prowizje, kto odpowiada za chargebacki, jak wygląda przepływ środków — po decyzji z P0 #4
- **Runbook:** provisioning utknął / płatność nie doszła / klient nie może się zalogować (sekcja 11 obecnej dokumentacji to zalążek — trzeba rozszerzyć)
- **Decyzje i ich uzasadnienia** (ADR): dlaczego destination charges, dlaczego własny HMAC zamiast Supabase Auth dla właścicieli, dlaczego cron co minutę

Ten dokument obsługuje dwóch odbiorców: **Ciebie za pół roku** i **każdego agenta**, który dostanie zadanie w tym repo. Bez niego agent musi wywnioskować zasady z kodu — a kod jest właśnie tym, co zawiera błędy.

# CZĘŚĆ 4 — Propozycja wdrożenia agentów

## Zastrzeżenie, które jest ważniejsze od reszty tej sekcji

**Nie buduj agentów marketingowych na systemie, który gubi strony klientów przy kolizji slugów i dopłaca do każdej rezerwacji.** Agenci marketingowi zwiększą napływ klientów, a każdy nowy klient to kolejna szansa na kolizję i kolejne prowizje z Twojej kieszeni. Automatyzacja pomnaża to, co już masz — również błędy.

Kolejność jest częścią propozycji, nie dodatkiem do niej.

## Warstwa 1 — Agenci operacyjni

Dziś system stoi na pięciu cronach, które **wykonują kroki, ale niczego nie sprawdzają**. Cron provisioningu wygeneruje stronę, wyśle maile i zaraportuje sukces, nawet jeśli strona wyszła pusta. Nikt tego nie zauważy, dopóki klient nie napisze.

Na tym polega przewaga agenta nad cronem: **agent może sprawdzić własną pracę**.

### A1 — Agent Provisioningu *(zastępuje `cron/provision-sites`)*

Cykl: znajdź gotowe zamówienia → sprawdź kolizję slugu → wygeneruj config → utwórz konto → **pobierz gotową stronę i oceń, czy wygląda poprawnie** → dopiero wtedy wyślij maile → zaraportuj.

Kluczowa różnica: krok weryfikacji. Agent pobiera `https://slug.nobooking.eu`, sprawdza, czy zdjęcia się ładują, czy opisy nie są zaślepkami, czy cennik ma sens. Jeśli coś nie gra — nie wysyła maila, tylko flaguje do przeglądu. Dziś nie ma tego kroku wcale.

Rozwiązuje przy okazji P0 #1, P1 #9, P1 #10.

### A2 — Agent Zdrowia Systemu *(nowy — dziś nie istnieje nic podobnego)*

Raz dziennie: błędy z Sentry, nieudane webhooki Stripe, rezerwacje wiszące w `pending` > 24 h, strony bez ukończonego Stripe Connect, subskrypcje wygasające w ciągu 60 dni, zamówienia utknięte w provisioningu. Jeden raport, priorytetyzowany, z propozycją działania.

**To agent o najlepszym stosunku wartości do wysiłku.** Wszystkie dane już masz — nikt ich nie ogląda. Wdrożenie: dni, nie tygodnie.

### A3 — Agent Wsparcia Właścicieli

Czyta pocztę od klientów, sprawdza kontekst w bazie (plan, status Stripe, rezerwacje), przygotowuje odpowiedź w wątku. **Ty zatwierdzasz przed wysyłką.** Przy 10 klientach zbędny; przy 100 to różnica między biznesem a etatem.

## Warstwa 2 — Agenci wzrostu (FB / IG)

### Co jest realne, a co nie

Zanim rozpiszę agentów — trzy rzeczy, o których lepiej wiedzieć teraz:

- **Meta Marketing API wymaga App Review** dla uprawnienia `ads_management`, zweryfikowanego Business Managera i konta reklamowego. To tygodnie, nie dni. Warto złożyć wniosek na starcie, bo czeka się niezależnie od reszty prac.
- **Instagram wymaga konta Business** połączonego ze stroną FB. Publikacja przez Graph API ma ograniczenia (limity postów, brak wsparcia dla części formatów).
- **Nie oddawaj agentowi autonomicznego wydawania budżetu.** Nie z powodu ograniczeń modelu — z powodu asymetrii: źle ustawiona kampania wydaje pieniądze szybciej, niż zdążysz zauważyć. Agent proponuje, człowiek zatwierdza kwoty.

### A4 — Agent Treści

Generuje kalendarz postów FB/IG dla nobooking.eu. Odbiorca jest B2B — właściciele apartamentów, nie turyści; to zmienia ton i tematykę (case studies, „ile kosztuje Cię Booking.com", zrzuty paneli). Posty trafiają do kolejki roboczej, nie na stronę. Ty zatwierdzasz.

Masz gotową amunicję, której nie wykorzystujesz: Casa Sol to działający dowód wdrożenia, a `docs/recovery/casasol_bookings_recovery.csv` zawiera prawdziwe dane o rezerwacjach.

### A5 — Agent Społeczności *(rozbudowa istniejącego bota)*

Fundament już jest — `facebook/webhook` obsługuje Messengera i komentarze. Rozbudowa: Instagram DM, wątki komentarzy, przekazywanie leadów do A3.

**Warunek wstępny: napraw P1 #12 (prompt injection).** Bot, który odpowiada publicznie na treści sterowane przez osoby trzecie, jest ryzykiem reputacyjnym — dziś ktokolwiek może skomentować post i sterować odpowiedzią pod Twoją marką.

### A6 — Agent Reklamowy

Czyta wyniki kampanii przez Marketing API, liczy koszt pozyskania leada w podziale na kreacje, proponuje przesunięcia budżetu i nowe warianty. **Tylko odczyt i propozycje** — zmiany zatwierdzasz Ty.

Wymaga wcześniejszego domknięcia atrybucji: dziś nie da się połączyć zamówienia z kampanią, bo `orders` nie ma pól UTM ani `source`. Bez tego agent nie ma czego optymalizować. To mała zmiana w schemacie, ale musi poprzedzić resztę.

## Na czym to zbudować

Masz już `@anthropic-ai/sdk` i działające crony na Vercelu — kuszące jest dołożenie kolejnych route'ów. Odradzam: sam napisałbyś wtedy pętlę agenta, obsługę stanu, ponowienia i harmonogram, a limit czasu funkcji Vercel (300 s) jest ciasny dla zadań wielokrokowych.

**Managed Agents** (Claude API, beta) pokrywa dokładnie ten kształt: Anthropic prowadzi pętlę i hostuje sandbox, konfiguracja agenta jest wersjonowana, a *scheduled deployments* uruchamiają sesje według crona bez własnego harmonogramu. Do tego dochodzą budżety sesji — twardy limit w dolarach na jedno uruchomienie, co jest właściwą odpowiedzią na obawę o niekontrolowane wydatki.

Bot Messengera zostaje tam, gdzie jest — pojedyncze wywołanie API w webhooku to nie jest zadanie dla agenta. Poprawki do niego: model na `claude-sonnet-5` (nowszy, o 33% tańszy), prompt caching na bazie wiedzy (~90% taniej dla cache'owanej części), structured outputs zamiast wymuszania JSON promptem.
